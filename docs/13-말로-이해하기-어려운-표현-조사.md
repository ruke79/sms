# 말로 이해하기 어려운 표현 — 740문항 전수 조사 (2026-09-06)

> 사용자가 Spring Q43 의 답변을 두고 **"대답이 좀 어려운 것 같다"** 고 했다. 원인을 보니
> 조건이 `내側이 REQUIRED 로 참여했고` 라는 **용어 안에 숨어 있었다.** 글로 읽으면 맞는 문장인데
> 말하면 듣는 쪽도 말하는 쪽도 한 번 멈춘다. 그래서 같은 결함이 나머지에도 있는지 전부 봤다.

## 0. 이 조사가 무엇이고 무엇이 아닌가 — 먼저 고지한다

- **문법 조사가 아니다.** 일본어 문법(조사·경어·문말)은 [`12-일본어-동사-전수-조사.md`](12-일본어-동사-전수-조사.md) 가 이미 했다.
  이 조사의 기준은 하나다 — **귀로 들었을 때 따라갈 수 있는가.**
- **사실관계를 바꾸지 않았다.** 47문항 전부 문장을 나누거나 가리키는 말을 이름으로 바꾼 것이고,
  주장·수치·결론은 손대지 않았다. `수정본/` 은 아예 건드리지 않았다 — 그쪽은 사실관계의 기준이고,
  말하기용이 아니다(`manuscripts/README.md`).
- **기계가 판정하지 않았다.** 스크립트는 후보만 뽑고, 고칠지는 사람이 읽고 정했다.
  그래서 이 검사는 **CI 에 넣지 않는다.** 이유는 §4 에 적었다.

## 2. 무엇을 결함으로 보았나

[`scripts/check-speech-clarity.py`](../scripts/check-speech-clarity.py) 가 다섯 가지 후보를 뽑는다.

| 범주 | 왜 어려운가 | 처음 후보 | 고침 |
|---|---|---|---|
| **전자/후자** | 듣는 사람이 두 항목을 머리에 담고 되짚어야 한다 | 21건 | **21건 전부** |
| **이쪽/그쪽** | 지시 대상이 멀면 못 따라간다 | 40건 | 26건 |
| **긴 문장** | 한 문장에 두 개 이상의 생각이 묶여 있다 | 90자 이상 58건 | 16문항 |
| **나열 4개 이상** | 개수를 안 밝힌 긴 나열 | 32건 | 4건 |
| **조건절 겹침** | 조건이 세 겹 이상 | 24건 | 3건 |

### 2-1. 전자/후자는 예외 없이 고쳤다

**이 범주만 오탐이 없었다.** 글에서는 되짚기가 눈으로 한 줄 위를 보면 끝나지만, 말에서는 되짚을
방법이 없다. 이름을 부르는 비용은 두세 글자뿐이다.

| 문항 | 전 | 후 |
|---|---|---|
| db Q50 | 전자면 리소스나 락, **후자면** 실행 계획의 변화 | **전부 느리면** 리소스나 락, **특정 쿼리만이면** 실행 계획의 변화 |
| java Q47 | 그래서 **후자는** 원래 리스트를 바꾸면 | 그래서 **`unmodifiableList()` 는** 원래 리스트를 바꾸면 |
| java Q85 | **후자를** 잊으면 상위 루프가 | **이 복원을** 잊으면 상위 루프가 |
| 회화체 Q160 | **앞엣것이면** 하이브리드 검색, **뒤엣것이면** 프롬프트 | **검색이 원인이면** 하이브리드 검색, **생성이 원인이면** 프롬프트 |

### 2-2. 긴 문장은 길이가 아니라 생각의 개수로 잘랐다

90자가 넘어도 **`A는 X, B는 Y, C는 Z`** 형태의 병렬 나열은 그대로 뒀다. 듣는 쪽이 같은 리듬을
따라가면 되기 때문이다. 반대로 60자대라도 **두 개의 독립된 생각**이 `〜て`·`〜고` 로 묶여 있으면 잘랐다.

- **자른 예** — spring Q41: `PostgreSQL 과 Oracle 은 READ COMMITTED, MySQL 은 REPEATABLE READ 가 기본이라 DB 를 옮기면 동작이 달라질 수 있다는 것은 염두에 둬야 합니다` → 기본값을 말하는 문장과 그래서 무엇을 조심하라는 문장, 둘로.
- **안 자른 예** — spring Q16(159자): `@ConditionalOnClass` 는 …, `@ConditionalOnMissingBean` 은 … 네 항목의 병렬. 길이는 식별자 이름 탓이고 구조는 단순하다.

### 2-3. 조건이 용어에 숨은 것 — 이 조사의 출발점

처음 지적받은 Spring Q43 이 이 형태였다.

| | 전 | 후 |
|---|---|---|
| 조건 | 안쪽이 **`REQUIRED` 로 참여**했고 거기서 예외가 난 경우 | **다른 빈의 `@Transactional` 을 부른** 경우 |
| 기제 | 안쪽이 **rollback-only 표시**를 하므로 | 공유하는 트랜잭션에 **"되돌려라" 표시**가 찍히므로 |
| 마무리 | (없음) | 없던 일로 만들 수 있는 건 **자기 메서드 안에서 난 예외뿐** |

같은 손질을 java Q35(`HashMap.put` 의 3중 분기), java Q106(마이크로벤치마크 3함정),
회화체 Q141(`Retry-After`)에 했다.

## 3. 분량은 늘리지 않았다

**쉽게 만들자고 길어지면 손해다.** 문장을 나누면 글자 수가 늘기 쉬워서, 고친 뒤에 반드시 다시 쟀다.
Q43 은 첫 판이 249자로 spring 145문항 중 두 번째로 긴 답변이 되어 **되돌려서 229자로 줄였다**
(세트 평균 185자 · 최대 276자). 전체로 보면 문장 평균은 35.4자이고, 90자를 넘는 문장은 27개만 남았다.

## 4. 이 검사를 CI 에 넣지 않는 이유

넣을 수 있는 형태로 만들 수는 있다. 넣지 않기로 했다.

**후보의 상당수가 오탐이고, 그 오탐이 정당한 문장이기 때문이다.** 나열 32건 중 28건은
"세 가지입니다" 로 개수를 먼저 밝힌 좋은 나열이었고, 이쪽/그쪽 40건 중 14건은 지시 대상이 바로 앞에
있어 아무 문제가 없었다. 이걸 실패로 처리하는 검사를 만들면, 통과시키려고 멀쩡한 문장을 망친다.
`docs/12` §10 이 오탐률 99.2% 를 적어 둔 것과 같은 이유다.

**기계가 할 수 있는 것은 후보까지다.** 그래서 스크립트는 건수만 출력하고 종료 코드로 판정하지 않는다.

```bash
./scripts/check-speech-clarity.py           # 범주별 건수
./scripts/check-speech-clarity.py 전자       # 그 범주의 문장을 전부 출력
```

## 5. 한계

- **소리 내어 읽어 보지 않았다.** "말했을 때"라고 했지만 실제로 발화한 것이 아니라, 문장 구조로
  판단했다. 일본어 발화의 자연스러움은 원어민 검수 영역이고 `docs/12` §11 의 한계가 그대로 남는다.
- **오탐으로 판단한 것에 근거를 다 적지는 않았다.** 병렬 나열과 가까운 지시어를 남긴 기준은 §2-2 에
  적었지만, 개별 문장마다 왜 남겼는지는 기록하지 않았다.
- **`수정본/` 과 `원본/` 은 검사 대상에서 뺐다.** 말하기용이 아니기 때문이다. 회화체와 수정본의
  문장이 이제 더 달라졌지만, 이는 애초에 의도된 관계다(`manuscripts/README.md`).
