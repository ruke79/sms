# Part 1. 구조·순서·전달 보증 (Q1~25)

| Q | 질문 | 키워드 |
|---|---|---|
| 1 | Kafka 를 쓰는 때 | 시간적 분리 + **같은 데이터를 여러 용도로** · 로그 보관 → 나중에 처음부터 재독 · 단순 큐면 더 가벼운 선택지 · 순서·재처리·다중 컨슈머·처리량 중 하나 |
| 2 | 토픽·파티션·오프셋 | 논리 이름 / 추가 전용 로그 / 연번 · **병렬도 = 파티션 수, 순서 = 파티션 안** · 거의 모든 제약의 출발점 |
| 3 🔴 | 순서 보장 범위 | **같은 파티션 안에서만** · 순서 단위를 키로 · 전체 순서 = 파티션 1 = 병렬도 포기 ✅`KAFKA-01` |
| 4 | 파티션 수 결정 | 처리량 + 컨슈머 최대 병렬도 · **나중에 줄일 수 없음** · 늘리면 키 할당 변화 · 너무 많으면 파일 수·리밸런스 ✅`KAFKA-05` |
| 5 🔴 | 컨슈머 그룹 | 같은 그룹 ID 끼리 파티션 분담 · 한 파티션 = 한 컨슈머 · **파티션 수 초과분은 놈** · 다른 그룹은 독립 재독 ✅`KAFKA-05` |
| 6 | 리밸런스 | 참가·이탈·파티션 변경·하트비트 끊김 · **그동안 처리 정지** · 최다 원인 = 한 건 처리가 폴링 간격 초과 · `max.poll.records` · 협조적 리밸런스·정적 멤버십 |
| 7 🔴 | `acks` | 0/1/all · 안 잃으려면 `all` + **`min.insync.replicas` ≥ 2 여야 의미** · 레플리카 하나뿐이면 `all` 도 소용없음 |
| 8 | ISR | 리더를 따라잡은 레플리카 집합 · `acks=all` 이 기다리는 대상 · **ISR 줄면 보장도 약해짐** → `min.insync.replicas` 아래면 쓰기 실패 |
| 9 | 프로듀서 멱등성 | PID + 시퀀스로 브로커가 중복 폐기 · 3.0+ 기본 켜짐 · **재시도 중복만** — 앱 이중 전송·컨슈머 중복은 별개 ✅`KAFKA-04` |
| 10 🔴 | Exactly-Once 보장 범위 | **Kafka 안에서 완결되는 범위만** · 트랜잭션 = 읽기·처리·쓰기·커밋 한 단위 · `read_committed` · 외부 DB/API 는 멱등 키 · "있으니 중복 대책 불필요"는 오해 ✅`KAFKA-04` |
| 11 🔴 | 오프셋 커밋 | 자동 커밋 = 처리 전 커밋 → **실패 메시지 유실** · 처리 후 수동 커밋 = at-least-once → **멱등 전제** |
| 12 🔴 | 컨슈머 랙 | 최신 오프셋 − 처리 오프셋 · **기울기를 본다** · 줄어들면 피크 흡수 중 / 계속 늘면 용량 부족 ✅`KAFKA-02` |
| 13 🔴 | 컨슈머 늘리면 빨라지나 | **파티션 수까지만** · 초과분은 대기 · 오토스케일 상한 = 파티션 수 · 병목이 외부 API 면 상대만 막힘 ✅`KAFKA-05` |
| 14 | 키 편중 | 한 파티션만 무거움 · 파티션별 랙으로 확인 · 접미사 분산 = **그 키 안 순서 상실** · 순서 필요하면 별도 토픽 ✅`KAFKA-06` |
| 15 🔴 | 처리 실패 메시지 | 그 자리 무한 재시도 = **뒤 전부 정지(독 메시지)** · 횟수 제한 → 재시도 토픽 → DLQ · 모니터링 후 되돌림 ✅`KAFKA-03` |
| 16 | 재시도 토픽 방식의 결점 | **순서가 깨짐** · 같은 키 후속이 먼저 · 순서 필요하면 파티션 안에서 막히는 것 수용 or 실패하지 않는 설계 ✅`KAFKA-03` |
| 17 | 보존 기간 | 재처리 소급 범위 + 디스크 · 며칠은 필요 · 최신값만이면 컴팩션 · **줄이는 순간 과거 소실** |
| 18 | log compaction | 키별 **최신 상태**만 · 설정값·마스터 배포 · 새 컨슈머가 전 키 최신 상태 획득 · 삭제 = `null` 툼스톤 · 이력에는 부적합 |
| 19 | 스키마 진화 | 스키마 레지스트리 호환성 강제 · **기본값 있는 필드 추가**는 양방향 호환 · 삭제·타입 변경·필수 추가가 위험 · CI 검증 · 파괴적이면 새 토픽 ✅`KAFKA-07` |
| 20 | 전방 vs 후방 호환 | 후방 = **새 스키마 데이터를 옛 읽는 쪽이** / 전방 = 옛 데이터를 새 읽는 쪽이 · **배포 순서로 결정** · 양쪽 만족 변경만 허용이 최안전 ✅`KAFKA-07` |
| 21 | 큰 메시지 | 그대로 흘리지 않음 · 상한 3곳(프로듀서·브로커·컨슈머) 맞춰야 · **본체는 오브젝트 스토리지, 참조만** · 압축 |
| 22 | 프로듀서 처리량 | `linger.ms` + `batch.size` 로 묶기 · 압축 · **지연 ↔ 처리량 트레이드오프** → 요건에서 무거운 쪽 결정 |
| 23 | Kafka 가 빠른 이유 | 추가 전용 로그 = 순차 쓰기 · 페이지 캐시 · 배치·압축 · **컨슈머가 오프셋 관리 → 브로커가 메시지별 상태 없음** |
| 24 | Kafka vs RabbitMQ | 로그 보관·독립 다중 소비·재처리·처리량 / 라우팅·메시지 단위 확인·우선순위 · 이벤트 배포 vs 작업 큐 |
| 25 | ZooKeeper → KRaft | 메타데이터를 Kafka 자신이 Raft 로 · 구성요소 감소·전파 빠름 · 신규는 KRaft · **ZK 현역 현장 많음 → 양쪽 아는 전제로** |

# Part 2. 설계·운영·장애 (Q26~50)

| Q | 질문 | 키워드 |
|---|---|---|
| 26 🔴 | DB 갱신 + 이벤트 발행 일치 | 한 트랜잭션 불가 → **Outbox** · 같은 트랜잭션에 발행 예정 기록 → 별도 프로세스 발행 · **받는 쪽 멱등이 세트** ✅`MSA-01` |
| 27 | 수신 멱등성 | 이벤트 고유 ID + 처리 ID 기록을 **같은 트랜잭션에** · 또는 "더한다"가 아니라 **"이 값으로 한다"** 조작 ✅`RES-01` |
| 28 | 순서 어긋난 이벤트 | 재시도·재처리로 깨질 수 있음 · 버전/타임스탬프로 **옛것 미적용** · 무조건 덮어쓰면 늦게 온 옛 이벤트가 새 상태 지움 ✅`MSA-02` |
| 29 | 이벤트에 담을 것 | 전부 담기(자기 완결·강결합) vs ID 만(약결합·조회 증가·**그때는 상태가 바뀜**) · 업무상 사실로 의미 있는 최소한 |
| 30 | 토픽 단위 | 소비 방식으로 · 같은 소비자·같은 방식 = 같은 토픽 · **이벤트 종류별이 아니라 애그리게이트별** → 순서 지키기 쉬움 |
| 31 🔴 | 트래픽 급증 흡수 | 순간 피크는 큐가 흡수 · **돌아오지 않으면 용량 부족** · 랙 기울기 · **큐는 시간을 벌 뿐 처리 능력을 늘리지 않음** ✅`MSA-03` |
| 32 | 컨슈머 느릴 때 순서 | 먼저 시간을 어디에 쓰는지(대부분 외부 I/O) · DB 접근 배치화 → 불필요 동기 호출 제거 → 그다음 파티션·컨슈머 · **순서 틀리면 부하를 하류에 떠넘김** |
| 33 | 다른 병렬화 | 한 컨슈머 안 병렬 · **어디까지 커밋해도 되는지 직접 관리** · 라이브러리 없으면 파티션 늘리기가 단순·안전 |
| 34 | Streams / Connect | Connect = 코드 없이 입출력(CDC 전형) · Streams = 변환·집계·조인 앱 · **단순 변환이면 평범한 컨슈머로 충분한지** 먼저 |
| 35 | CDC 를 Kafka 로 | 앱 무수정 · **DB 스키마가 그대로 하류로 → 결합 강화** · 삭제 이벤트에 PK 만 · 순서·중복·초기 스냅샷 부하 |
| 36 | 레플리케이션 설정 | RF 3 기본(1 이면 브로커 하나 죽으면 읽기쓰기 불가) · `min.insync.replicas` 2 · **두 대 죽으면 쓰기 정지 = 깨진 데이터 안 만드는 선택** |
| 37 | unclean leader election | ISR 밖 레플리카를 리더로 · 가용성 ↑ 대신 **못 따라잡은 데이터 소실** · 기본 비활성 유지 · 가용성 vs 일관성을 설정으로 고르는 예 |
| 38 | Kafka 모니터링 | 랙·ISR 이탈·리더 없는 파티션·디스크·네트워크 · **값보다 기울기** · 리밸런스 빈도 · **대피 토픽 유입 증가 = 조용히 깨지는 중** |
| 39 | 컨슈머 정지 감지 | 랙 증가 + 커밋 정지 · 프로세스 살아도 할당 상실·한 건에 막힘 가능 · **"살아 있나"가 아니라 "진행하나"** · 마지막 커밋 시각 |
| 40 | 랙 급증 조사 | **입력 증가 vs 처리 저하** (발행 레이트) · 외부 I/O → 리밸런스 → 독 메시지 순 · 특정 파티션만이면 키 편중 · **전부인지 일부인지** 먼저 |
| 41 | 과거 이벤트 재처리 | 새 컨슈머 그룹으로 처음부터 · 기존 그룹 오프셋 이동은 위험 · **하류 부수효과가 두 번 나가지 않는가** · 보존 기간 밖은 불가 |
| 42 | 컨슈머 배포 | 재시작마다 리밸런스 → 정적 멤버십 · **스키마 호환성 확인 후** · 프로듀서/컨슈머 선후로 필요한 호환성 결정 |
| 43 | 동기 vs 비동기 통신 | 결과 즉시 필요 → 동기 · 통지·파급 → 비동기 · **결과적 일관성 수용 + 화면 표현까지 설계** · 전부 비동기 = 추적 불가 |
| 44 | Saga | **로컬 트랜잭션의 연쇄** + 보상 · 주문·재고·결제 · **보상이 정말 가능한지 먼저** · 취소 불가 부수효과는 마지막에 |
| 45 | 분산 트레이싱이 Kafka 를 넘나 | 그대로면 끊김 · **메시지 헤더에 트레이스 정보** · 계측 라이브러리 자동 전파 · 로그에도 같은 ID ✅`OBS-01` |
| 46 | 보안 설정 | TLS + SASL + ACL 토픽 단위 · **개발 편의를 운영에 그대로** = 누구나 전 토픽 읽음 · 클라이언트별 최소 권한 |
| 47 | 개인정보 이벤트 | 애초에 담지 않기 · 참조 ID · 짧은 보존·암호화 · **로그는 추가 전용 = 개별 삭제 불가** · 키 폐기로 실질 복호 불가(설계 시 결정) |
| 48 | 테스트 | 로직은 단위 · Kafka 결합은 **실제 브로커**(임베디드/컨테이너) · 목만으로는 직렬화·리밸런스·커밋이 미검증 |
| 49 | Kafka 를 넣지 말아야 할 때 | 소규모 단순 큐 · **운영 부담 > 구현** · 요청·응답형 부적합 · "비동기면 빨라진다"는 착각 · 순서·재처리·다중 소비·처리량 중 무엇이 필요한지 말할 수 있어야 |
| 50 | 장애 시 첫 확인 | 영향 범위(전 토픽/특정 파티션·브로커/컨슈머) · 브로커 생사 → 리더 없는 파티션 → ISR → 랙·리밸런스 이력 · **즉시 복구와 재발 방지 분리** · 시각·조작 기록 |

# 💡 사용 순서

1. **매일 아침 5분** — 그날 학습할 6문항의 키워드만 훑기
2. **학습 중** — 키워드만 보고 일본어로 말하기 → 녹음 → [`Part1`](../kafka-면접/Part1.md)·[`Part2`](../kafka-면접/Part2.md) 원문 대조
3. **✅ 문항은 한 번은 돌려 본다** — 실물 브로커가 필요하므로 `docker compose up -d --wait` 뒤에
4. **면접 전날** — 함정 8개 + S급 10문항 키워드만
5. **면접 당일** — [`필수-키노트`](../kafka-면접/필수-키노트.md) 의 **일본어 한 문장 10개**
